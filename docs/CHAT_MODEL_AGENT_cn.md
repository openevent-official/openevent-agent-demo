# Chat Agent

> 实现状态：本文的事件驱动会话、上下文压缩、过长消息拒绝及配置已实现。

[English version](CHAT_MODEL_AGENT.md)

Chat Agent 在一个部署内服务指定用户与 Agent 之间的多个 Chat 会话。不同会话有各自的输入队列、工作目录
和模型历史，共用部署绑定的 Model、Cmd 和 WAL Channel。完整部署入口见
[Runtime Reconciler](RUNTIME_RECONCILER_cn.md)；本文规定 Agent 自身的运行配置并说明使用行为。
持久字段和源事件引用统一见 [Agent WAL 协议](AGENT_WAL_PROTOCOL_cn.md)，当前协议为 `agent.wal.v5`，模型 I/O 版本为 `4`。
模型输入、摘要、压缩请求、工具与输出格式统一见[模型输入输出格式](MODEL_IO_cn.md)；该文档也提供默认提示词与完整请求示例入口。
同一会话按事件推进，模型调用与实际工具执行分别串行；等待工具不会阻止新用户消息触发模型。
空闲或等待结果的会话不独占工作线程，增加会话不会增加工作线程数。

本文维护配置和使用契约，不为旧代码保留兼容分支。
会话读取见[会话发现](#会话发现)，持久字段见 [WAL 协议](AGENT_WAL_PROTOCOL_cn.md)。
正文只合并完整模型片段、不拆分，来源使用 seq 范围。
来源字段见 [WAL 显示来源](AGENT_WAL_PROTOCOL_cn.md#5-副作用意图和显示来源)。

## 安装和启动

在部署使用的 Python 环境中安装并启动 Agent。构建命令及依赖的安装方式见[构建与安装](../README_cn.md#构建与安装)。
整套服务的准备步骤见 [Ubuntu 环境文档](UBUNTU_ENVIRONMENT_cn.md)，运行条件见 [Runtime 的依赖要求](RUNTIME_RECONCILER_cn.md#依赖)。

```bash
make install PYTHON=python3
chat-model-agent --config /etc/openevent-agent/agent.json
```

运行时检查已安装 SDK 和模块的公开能力；OpenEvent SDK 缺失、版本不满足声明或被源码路径覆盖时启动失败。
模型 Provider 凭据配置在 Model Proxy，不能放进模型消息。

## Agent 配置

配置文件是 UTF-8 JSON，版本固定为 `chat-agent.v1`；未知字段、重复字段和非法类型会报错。
通常由 Runtime 生成，下面展示结构，示例 principal、token 和 Channel ID 必须替换为部署实际值：

```json
{
  "version": "chat-agent.v1",
  "deployment_id": "local-chat-agent",
  "openevent": {"target": "127.0.0.1:9527"},
  "agent": {
    "principal": 90002,
    "token": "replace-with-agent-token",
    "user_principal": 10001,
    "system_prompt": "此处由 Runtime 写入完整系统提示词正文。",
    "context_compression_prompt": "此处由 Runtime 写入完整上下文压缩提示词正文。",
    "context_max_input_bytes": 1048576,
    "model": "replace-with-model-name",
    "work_root": "/var/lib/openevent-agent/work"
  },
  "model_proxy": {"principal": 20001},
  "cmd_worker": {"principal": 30001},
  "channels": {"model": 101, "cmd": 102, "wal": 103},
  "rpc": {"max_retries": 3, "timeout_ms": 10000}
}
```

除 `rpc` 外，示例中的顶层字段及 Agent 字段都是必填项。`deployment_id` 标识本次部署；
`channels` 是已经绑定的三个不同辅助 Channel，不是 Chat 会话列表。Agent 与用户 principal 必须不同。
`system_prompt` 是完整系统提示词，可为空；`context_compression_prompt` 是完整压缩提示词，必须有非空白内容。
Agent 直接使用这两段 UTF-8 正文，不读取源提示词文件，也不追加代码内置的另一份协议提示词。
文件路径与更新入口由 [Runtime 提示词文件](RUNTIME_RECONCILER_cn.md#提示词文件)定义。
`context_max_input_bytes` 必填，无默认值，含义见下节；示例值不代表任何模型的 token 窗口。
工作目录路径必须是绝对路径，表示部署数据目录，不依赖开发机工作区。
单独运行 Agent 时也须满足 [Runtime 的工作目录部署前提](RUNTIME_RECONCILER_cn.md#目录结构)。

`openevent.max_payload_bytes` 可选，默认 `16777216`（16 MiB），取值为 `1..62914560` 的整数。
它是目标 OpenEvent 服务端的 payload 额度。Runtime 写入服务端实际配置值，单独运行 Agent 时也应与目标服务端保持一致。Agent 将同一额度传给每个会话的 Chat SDK 客户端。
Agent 按实际编码后的 payload 字节数检查自己构造的业务内容及 WAL 记录，包括 Chat 正文与固定通知、
普通和压缩准备记录、工具准备/发送/完成记录及实际 Model、Cmd 请求；尚未分配的标识按最大合法编码宽度预留。
另行检查包含附件凭据和封装的 64 MiB 传输上限。
Chat 结束清单由 SDK 构造并按其公开契约处理超限；Agent 接受 SDK 发布的错误结束，并采用其空正文、空附件终态。
该额度不包含消息封装或附件凭据，也不按原始正文或工具参数的字符数计算。

模型来源的展示大小检查使用本回答准备时固定的 `turn_id`，并将 `pre_seq` 按 uint64 最大值预留。
每个完整非空正文片段按对应的 reset 或 append 计量；需要整体替换的完整响应或拒答按 reset 计量，均检查完整 payload 与传输封装。
这样同一来源不会因当前展示链尾、取消或重启而得到不同的大小判定。实际发送时仍按真实字段再次检查完整消息。

Agent 可选项：

| 字段 | 默认值 | 含义 |
| --- | --- | --- |
| `model_provider` | 不指定 | 交给 Model Proxy 选择的 Provider 名称 |
| `model_timeout_ms` | `60000` | 普通与压缩请求共用，从原模型请求顶层 `ts_ms` 起算的当前等待超时，毫秒 |
| `model_retry_interval_ms` | `1000` | 普通推理和历史压缩共用的固定重试间隔，正整数毫秒；见[模型重试间隔](#模型重试间隔) |
| `max_model_attempts` | `3` | 同一份普通模型输入的最大尝试次数，包含首次调用；压缩使用[上下文字节预算](#上下文字节预算)中的固定额度 |
| `max_model_concurrency` | `4` | 当前 Agent 进程同时推进和等待结果的普通及压缩模型尝试数上限 |
| `cmd_result_timeout_ms` | `330000` | 从工具请求顶层 `ts_ms` 起算的当前等待超时，毫秒 |
| `max_tool_output_bytes` | `32768` | 每个工具结果、每个输出流给模型的原始字节额度 |
| `output_read_chunk_bytes` | `32768` | Agent 每次向命令服务读取标准输出 stdout 或错误输出 stderr 时请求的字节数上限 |
| `idle_sleep_ms` | `50` | 事件读取已到尾部且本次没有消息时的空闲等待时间，毫秒；有消息或仍有未读页时立即继续读取。模型、工具结果和正文合批按事件或各自截止时间唤醒，不使用此等待 |

不提供 `agent.discovery_interval_ms` 或独立发现循环；Runtime 不生成该字段，Agent 不接受它。

`max_model_concurrency` 控制 Agent 的调度名额。需要发送模型请求或继续处理模型结果的尝试，在进入这一阶段前取得名额，
等待结果、确认展示和记录裁决期间仍占用，退出该次尝试的处理时释放；实际工具执行不占此名额。普通调用与压缩共用该额度，且每个会话最多有一个受 Agent 调度的模型尝试。
重启后，已有未结束请求同样等待名额才能继续处理，但后台任务可能仍在运行，因此这个值不限制
所有已发出但尚未结束的请求总数。Model Proxy 的实际执行并发由 Runtime 的 `model.max_concurrency`
单独控制，见 [Runtime 配置](RUNTIME_RECONCILER_cn.md#配置)；Agent 的工作线程数也独立于此设置。

数值选项要求正整数，不接受 boolean。`rpc.max_retries` 可以为零，表示不在首次失败后重试；
单次 RPC 等待必须为正整数。所有 Agent RPC 的重试间隔内部固定为 100 毫秒，与当前 Chat SDK 一致；
不提供 RPC 重试间隔配置项。默认最多重试 3 次，单次 RPC 等待 10000 毫秒。
RPC 重试额度与模型业务尝试额度分别计算，不叠加 SDK 内部重试形成额外次数。

### 模型重试间隔

`agent.model_retry_interval_ms` 可选，默认 1000 毫秒，普通推理和历史压缩重试共用。只有失败可重试且尚有尝试额度时，
才等待这个固定间隔后开始下一次模型尝试。首次尝试不加这段等待；成功、不可重试或尝试额度用尽后也不等待。

间隔从上次已确认的 `attempt.fail` 记录顶层 `ts_ms` 起算，使用当前运行配置中的值。
该配置不冻结进 WAL；重启时仍从原失败时间计算，只等剩余时间，间隔已过则可继续重试。
等待只发生在创建下一次尝试前；若该尝试的 `attempt.prepare` 已确认，恢复时直接续行，即使当前间隔增大也不重新等待。
等待不占全局模型名额，期间仍响应用户取消和停机。

这是固定间隔，不读取 Provider 的 `Retry-After`，不做指数退避，也不限制每分钟请求数（RPM）。

## 上下文字节预算

`context_max_input_bytes` 记为 `B`，是正整数，不接受 boolean。
计量对象是完整 JSON 请求内容，按以下统一规则编码为 UTF-8 后计算大小：对象键按 Unicode 码点字典序排列，数组顺序不变，
无额外空白、不转义非 ASCII 字符、禁止非 JSON 数值。普通和压缩输入的 user.content 采用同一规则；
系统提示、模型消息、摘要、事件中的调用参数、附件描述、工具定义及其他请求字段都计入。
这是 Agent 的逻辑输入计量；Model 事件外壳与传输封装另行计量。
普通请求和压缩请求按上述规则计量均不能超过 `B`，并且还必须通过上节的 OpenEvent payload 与传输检查。
它不是 token 数，也不保证任意模型都能接受；不使用固定字节比例换算 token，不另设输出 token 参数。

运行时还要按上述计量口径计算当前 Model 发布能容纳的最大 body 字节数，并为完整 Model 事件外壳与凭据等传输封装留足空间，
使完整消息同时满足 OpenEvent payload 额度与 64 MiB 传输限制。
取 `C = min(B, 当前可发布的最大 body 字节数)` 作为有效运行上限；`C` 不是新配置项，也不改写配置中的 `B`。
`B` 大于发布容量不构成配置冲突，不因此拒绝启动。

按有效运行上限计算两种固定基线，计量请求仅用于计算，不发送给模型：

- `F_normal`：完整普通请求，保留系统提示词、工具定义及固定字段，`events=[]`；取 `summary=""` 与 null 两种编码大小的较大值。
- `F_compression`：完整压缩请求，保留压缩提示词及固定字段，`events=[]`；取 `summary=""` 与 null 两种编码大小的较大值；
  `max_summary_bytes` 暂用 `C` 计量，保守预留目标数字的编码宽度，再求真实目标，避免循环计算。
- `F = max(F_normal, F_compression)`；`T = floor((C - F) / 2)`。`F`、`T` 随有效运行上限推导，不增加用户配置项；奇数余下的一个字节不用。

`T` 同时是**压缩后整个历史的硬上限**和**单条完整输入事件的上限**。实际压缩请求携带 `max_summary_bytes=T`。
历史包括摘要正文和仍未压缩、且排在下一条待处理输入之前的全部旧事件；不能只检查摘要字符串。
摘要正文使用同一上限，不另设额度。

所有增量仍按最终请求编码后的字节计算：摘要取普通或压缩请求中以正文替换空摘要字符串后的增量较大值；
单事件取将该完整事件放入空 `events` 数组后、最终请求 body 的字节增量，再保守加一个数组逗号的字节。
两种请求采用相同事件编码；历史计量值为摘要增量加所有剩余旧事件的上述计量值。空历史计为 0。
即使只有一个事件也计入这一个逗号，因此不会漏掉后来追加事件的分隔开销。换行、引号、反斜杠的两层 JSON 转义全部计入，
不是正文原始 UTF-8 字节或 token 数。没有实际摘要时仍使用 null，空摘要字符串只用于基线计量。

有效运行预算能容纳下文的最小必要事件时，保证由下式成立：
`完整请求大小 <= F + 历史计量值 + 单条新事件计量值 <= F + T + T <= C <= B`。
因此历史达标后，**任何按本次有效预算通过单事件准入的用户消息或工具结果都至少能接收一条**；不依赖它刚好很短。
例如配置 `B=100000`，当前发布容量只能容纳 60000 字节 body，且重算的 `F=20000` 时，`C=60000`、`T=20000`：
历史整体最多 20000 字节，再加入最多 20000 字节的一条合规事件仍能发布；不能等请求接近配置的 100000 字节才开始压缩。
实际发布时，Agent 检查 Model SDK 为该模型尝试准备的完整 payload；检查、发布及同一次 SDK 发布调用内的重试使用同一份字节。
准备对象的公开契约见 [Model SDK API](https://github.com/openevent-official/openevent-modules-model-proxy/blob/main/docs/SDK_API_cn.md#22-输入模型)。
其他 Chat、Cmd 和 WAL 发布继续按各自实际记录检查，不能用此公式替代它们的协议限制。

每条用户消息（包含附件描述与回复引用）和每个规范化模型输出事件都按对应的单事件上限 `T` 准入。
一次模型输出仍须整体校验、整体接受；任一完整事件超限则整份输出失败且不执行其中的工具，但不要求多条合法事件的合计也小于 `T`。
已接受工具的结果按 `min(所属回答冻结的 T, 当前配置 B 推导的目标)` 检查；仅 `C` 降低不把旧工具结果变成致命错误，
后续模型请求和压缩仍受当前 `C` 限制。工具结果超限使用既有短错误，原结果保留。
完整调用参数留在原调用事件及执行记录中，历史压缩后不附加完整参数表。

准备回答时，用本批完整回复目标构造未来 `user_cancelled` 事件并检查 `T`；超限就缩短新事件前缀，剩余事件留给后续回答。
只有工具结果触发时也检查合并后的来源用户目标；单项结果沿用原回答已检查的目标范围，不等用户取消时才丢目标。
接受工具前，用实际参数构造它可能需要的完整短错误，例如读取结果中的 `exec_id`、`offset`、`nbytes`，并确认其计量值不超过 `T`；
其余有上界字段预留最大合法宽度。这样达标历史与该错误必能合并。

配置自身的合法性按同一套规则、仅使用 `B` 计算基线与准入目标：目标必须为正，且最小有效 user 事件
（`text="a"`、`attachments=[]`、无回复引用）及完整必要短错误都能通过准入。配置自身放不下这些内容仍是配置错误。
启动时不因 `B` 超过 OpenEvent 发布容量报配置错误，也不预检固定通知能否发送；固定拒绝通知和失败通知在实际发送路径检查完整编码。

若仅因当前发布容量较小，使按 `C` 推导的预算连最小请求或必要短错误也容不下，不全局拒绝启动，
也不把所有用户消息判成过长。此时暂保留仅按配置 `B` 推导的基线和普通输入准入目标，
不把保守预算推导失败当作禁止模型请求的条件。新请求和已冻结请求都按具体正文及完整编码检查：实际能发送就继续执行，
仍放不下才记录本地失败、通知并暂停。冻结请求不受当前新提示词的基线推导阻止。
若准备记录或通知本身也无法发布，才按既有规则报告部署额度不足并退出。

上述例外不放宽压缩容量。压缩目标始终为 `max(0, floor((C - F) / 2))`，正常情况下就是 `T`；
即使普通输入准入暂用配置目标，历史也按这个实际压缩目标判断是否需要压缩，新压缩准备保存该目标。
目标为 0 或下一条完整旧事件放不进 `C` 时，转入既有压缩失败回退；回退的具体普通请求仍能发送时可以继续，否则本地失败。

配置更新的兼容检查仍使用当前 `B` 与提示词推导的配置目标，检查仍需进入模型的单个历史事件、已采用摘要、
未结束回答的取消目标及已接受工具未来的短错误；不再合规时报告配置不兼容并退出。
尚未完成的普通或压缩模型阶段若冻结的 `T` 大于该配置目标，也拒绝启用新配置。
仅有发布容量下降、导致有效 `C` 或 `T` 变小，不据此拒绝整个 Agent 恢复；历史总量超过运行目标时先尝试压缩，无法容纳的请求走本地失败流程。
已固定请求沿用原配置、来源和派生目标快照，字段见 WAL。已发布的模型请求和已裁决来源继续按原事实读取结果，
不因当前发送容量变小撤销结果；未发布请求不改正文或重选来源，继续发布前按当前实际额度检查，超限则本地失败。

准备下一次普通输入时，先找到下一条待处理的用户消息或正常工具结果，检查它之前的整个旧历史。
历史不超过上文的实际压缩目标就已经达标；超过则先压缩完整连续旧事件，直到摘要加剩余旧事件的总量不超过该目标，再加入这条新输入。
额外新事件只有在完整请求仍满足有效上限 `C` 时才继续选入，未选事件留队，不能用更多新事件挤掉保证的一条输入。
压缩沿用普通模型、Provider、timeout 和调度名额。每批请求只选能放下的完整前缀，摘要输出计量值必须不超过本批冻结的压缩目标，
每批最多 2 次尝试，失败重试不改原输入。每份合格摘要可立即成为检查点，但残留旧历史仍超过实际压缩目标时必须继续，不能宣布压缩已经达标。
不要求每一批都比原前缀更短；每批成功必须向前覆盖至少一个完整事件，最终按整个历史的硬目标验收。
已确认历史输出可直接压缩，未处理新用户消息和正常工具结果保留原事件，范围见 [WAL 压缩检查点](AGENT_WAL_PROTOCOL_cn.md#4-事件引用顺序与压缩检查点)。

摘要超限判定该尝试失败，流式发现超限即请求取消，不截断后接受。无法得到达标历史时，最后已提交摘要加尚未覆盖事件组成的普通请求若仍合法可继续，
否则沿既有模型失败通知与暂停流程处理；不撤销已提交检查点，未达到目标不能标记为压缩成功。
仅为记录这种发布前的本地失败时，`answer.prepare` 可以保存仍超过有效上限 `C`（也可能超过 `B`）的候选输入来源；
请求是否可发仍遵循上文对冻结请求的检查规则，单事件准入仍遵循正常运行或有效预算不足时的规则。
该准备记录及失败通知本身仍须通过各自发布额度检查，记录方式见 [WAL 协议](AGENT_WAL_PROTOCOL_cn.md#3-data-字段)。
失败批次结束后保留其尝试记录。后续新输入的处理可以再次压缩相同历史范围；已暂停的会话由下文规定的有效新用户消息恢复。
这里保证的是“达到目标后一定有一条合规输入的空间”，不保证模型每次都能生成合格摘要，也不替代 Provider 的真实 token 限制。
原始 OpenEvent 历史、Agent 内存与磁盘输出不受这项模型输入预算限制。
Agent 在内存中维护当前摘要和未覆盖消息及其直接引用内容，已覆盖的独立历史正文需要时从 OpenEvent 读取，不另设历史正文缓存。
新消息引用已覆盖原文时，该引用内容随新消息保留到新消息也被摘要覆盖；Chat 的回复位置引用保持不变。
必要的历史定位信息和未完成任务状态仍保留，压缩不删除 OpenEvent 原始记录，也不代表整个进程内存固定。

## 过长用户消息

Chat Server 的单条正文限制是入口检查，额度由 [Runtime 的 Chat 配置](RUNTIME_RECONCILER_cn.md#配置)传入；
它不计算模型提示词、工具、附件描述或回复引用。Agent 因此仍独立检查模型输入，不假定通过 Chat 的消息一定能放入模型。

Agent 对尚未消费的每条用户消息执行上节的单事件准入，包含全部附件描述和回复引用，完整编码计量值必须不超过 `T`。
不能只比较用户文字长度；有效运行预算满足上节最小必要条件时，这个上限同时保证该消息能和达标历史一起参与普通推理，
也能和达标摘要一起完整进入压缩请求。

单事件超过上限时，Agent 直接用 Chat `single_turn` 回复 **“Message is too long to process.”**，只回复该条原用户消息。
不先显示处理占位，不调用普通或压缩模型，不消耗模型尝试，不因这次拒绝冻结会话。
这次拒绝独立记录，不以此前积压记录的处理进度为前提，也不触发一次新推理；正常运行时，其他消息和工具仍按原有调度推进，不等待拒绝通知完成。
会话已经暂停时，被拒绝的消息不会解除暂停，也不会唤醒旧积压；恢复条件见[会话和回答](#会话和回答)。
用户可缩短正文、减少附件或回复引用后重新发送。拒绝的消息保留在 Chat 历史中，
但其正文、引用内容和附件不进入后续模型事件或压缩材料；拒绝通知本身也不是模型生成的 assistant 事件。
用户后来主动引用这条已拒绝消息时，引用内容属于这次新输入，仍按单事件上限重新计量：放得下可以处理，放不下再拒绝。
此时引用正文和附件只随新输入及其后续摘要出现，不恢复原被拒消息的独立历史事件。

拒绝先持久保存，通知复用现有 Chat 发送意图与确认，重启不会重复处理该消息或另发一条通知；
字段及消费边界见 [WAL 协议](AGENT_WAL_PROTOCOL_cn.md#3-data-字段)。通知发布结果未明时核对该发送意图，不借此触发推理或提前推进历史消费边界。
重启后，会话先核对并补齐已记录拒绝的未完成通知，确认完成后才恢复处理新输入；后续普通回答已经推进，不代表此前拒绝的通知已经完成。
这只是不让模型处理一条放不下的输入，不取消已经接受的工具或其他回复。

若单条消息通过准入、实际请求只是累积历史过长，先按上下文压缩规则处理；压缩失败后仍不能形成合法请求，
才使用下文的模型失败通知与等待流程，不能谎报当前用户消息过长。Provider 实际返回的上下文超限也按模型失败处理，
不把已经固定或尝试过的输入追认成上述本地拒绝。

## 会话发现

Agent 从 OpenEvent 系统消息自动发现会话，接管所有使用 `chat.v1` 且 Agent principal 已加入的 Channel。
创建者、可见性、名称、成员人数和部署 user principal 不增加接管门槛；仅有读取权限不代表接管。
用户输入及取消仍按配置的 `user_principal` 判断。新建会话无需重新 apply 或重启 Agent、worker。

部署方须保证 Agent 在首条 Chat 业务消息之前加入，可以在创建时加入，也可以创建后立即加入；
不把 Agent 加入已有业务历史的旧 Channel，也不移出 Agent。Agent 进程可以离线，稍后仍会读取加入后的消息。

每次启动从保留的 OpenEvent 历史恢复会话与未完成工作，再处理新输入；回放不会重新执行已经完成的动作。
发现与消息接收共用 Fetch，不需要单独的发现间隔或会话清单。它也会读取其他可读 Channel 的业务数据，
不承诺减少网络流量。停止、重启及历史保留要求见[停止、重启和排错](#停止重启和排错)。

## 会话和回答

Agent 自动生成的固定提示和失败原因统一使用英文；用户消息、模型回复和工具原始输出保留原文。

用户输入只使用完整的 Chat `turn.single`，包括只有附件没有文字的消息。
Agent 回答仍然流式展示：先出现“Processing...”，再由模型正文替换并继续追加。模型只返回工具调用也有效。
若最终接受的输出只有工具调用，没有正文或拒答，等这条回复的直接工具都有结果且必要清理完成后，
仍打开的回复会把占位替换为“Tool processing has ended.”再结束；已有模型正文保留，已取消或已结束的回复不改写。
这个提示不代表命令成功或用户整个任务完成，也不作为模型回答进入后续历史。
新用户消息和真实工具结果按原始 OpenEvent 事件顺序进入会话，日志不会为了靠近某条工具调用而移动结果。
模型结果、失败、有效取消和到期触发也按原事件 seq 决定处理结果；正常运行与重启使用同一规则。
模型终态或明确失败来源先于取消时，先保存该结果，后来的取消只停止尚未发送的动作并清理在途工作；
取消先于模型来源时，不再接受其后输出。回复已取消时不补正文，但不丢弃此前已经成立的结果。
每次普通模型输入由完整系统提示词、已经确认的摘要、摘要之后的事件历史和本次新增事件的连续前缀组成。
历史摘要由模型保留任务编号、目的和必要事实，不另附完整工具参数清单。
后来的工具结果仍按顺序进入 `events`，通过任务编号联系摘要中的工作；执行、取消和恢复始终使用原始记录中的精确参数与归属。
完整格式和连续两次调用的对比见[请求示例](examples/README_cn.md)。

每个会话最多有一个模型尝试，包括压缩；实际工具按接受顺序 FIFO 执行，同一会话最多一个实际工具执行槽。
模型返回的原生 `tool_calls` 用于分派，随后作为事件进入历史；不制造“已接收”、queued 或 pending 的原生工具回执，
也不要求把每条原生调用和结果配齐后才允许下一次模型请求。真实结果仍按来源关联原调用。
例如 A 请求的工具尚在运行时，B 的完整用户消息可以触发下一次模型调用；模型结合事件历史与摘要保留的调用引用理解进展。
新调用产生的工具继续排入同一队列，不与已经执行的工具重叠。

多个回复可以同时等待各自工具，每个回复保留自己的工具归属、回复目标和取消范围。
用户取消只作用于指定回复：尚未派发的工具停止派发，已派发的命令请求清理；其他回复和新用户消息仍可继续推进。
发出 kill、等待超时或记录模型可见的工具失败，都不能证明命令已经停止；实际工具槽只在真实 Cmd 终态确认后释放。
迟到终态用于结束实际执行占用，不改写已经确认的超时或取消裁决，也不重新执行命令。
分块输出读取取消后不再发布下一块，仍按实际在途请求完成情况收尾。

每次准备输入时固定摘要引用及其覆盖边界、事件范围和提示词；重试和重启不插入后来事件，
也不因文件更新重新解释已准备请求。输入范围和关联字段见 [WAL 协议](AGENT_WAL_PROTOCOL_cn.md)。
新的完整用户消息与非用户取消收尾的最终工具结果按上述顺序触发工作；工具成功、业务失败和等待超时均包括在内。
没有这类事件时等待，不用伪工具回执驱动循环。
上下文压缩只替换模型下一次阅读的旧事件表示，不删除 OpenEvent 原事件，也不改变工具的实际状态和归属。

可重试的普通模型失败按 `max_model_attempts` 处理；压缩失败使用上节固定额度。
Model Proxy 返回 `infer.result` 状态码 `60009` 时，表示请求中固定的服务商名称未配置。Agent 将该次失败记为不可重试，错误日志记录原请求的 seq 和服务商名称。普通回答直接进入失败通知和暂停流程，压缩批次结束并按已有压缩失败流程回退。
尝试额度耗尽、普通请求使用了未配置的服务商、Provider 明确报上下文超限或历史压缩后仍无法准备合法输入时，保存最终失败原因，发布一次独立 Chat single，
回复目标沿用本次回答的固定目标，正文为“Processing failed: {reason}. This conversation is paused. Send a new message to retry or revise your request.”。
原因采用 Agent 定义的固定英文短诊断，说明失败阶段和实际原因，例如“Normal inference timed out waiting for the model response”、
“History compression timed out waiting for the model response”、“History compression produced a summary that exceeds the size limit”
或“Normal inference returned invalid tool arguments”，不只显示笼统的模型调用失败，也不直接转发整段服务错误或模型输出。
压缩请求在发布前超过大小上限时，报告“The history compression request exceeds the size limit”；只有模型返回的摘要超限才报告摘要过大。
压缩失败导致普通请求也无法发送时，通知保留具体压缩原因，不能改说当前用户消息过长；通知从已经保存的最终失败原因重建。
如果确定本地失败时尚未创建正常回复，就直接发送上述失败通知，不补发处理占位再取消，也不创建空回复。
本次失败处理在通知与暂停事实确认后结束；失败裁决确认后的恢复只补尚未完成的记录或通知，不等待不存在的正常回复关闭。
最终失败来源先于有效取消时，仍补齐失败通知和暂停，同时完成取消清理；取消先发生时，不因其后的模型失败新增暂停。
会话暂停新的普通推理，由用户决定是否重试或调整请求。新用户消息先完成自身内容和大小检查，
只有已检查前缀中第一条通过检查、且源事件晚于失败通知的 `turn.single` 才能解除暂停；检查后新到的消息先等待自身检查。
单条用户消息的本地拒绝按[上节](#过长用户消息)处理，不新增冻结，也不解除已有暂停。
已有积压输入和工具结果不能单独解除等待。已经接受的工具继续执行并保存结果，仍打开的回复可以分别取消；
模型失败不会自动撤销或重跑工具。新用户消息解除等待后，继续按事件顺序处理；需要压缩时可以创建新的批次，范围可以与失败批次相同。
新批次使用本身的尝试额度，旧批次的失败记录保持不变；单纯重启不会解除暂停或重新开始已失败的批次。
不重复发送同一份不可能放下的输入。明确拒答直接展示，不因拒答重试。
一条用户消息、附件描述、必要工具结果或工具参数不能为凑额度而被静默截断。
完整模型输出中的任一事件若未通过准入，整次输出不接受、不执行其中任何工具，按模型输出失败处理；已经展示的流式片段沿用原有失败与重试流程。
工具真实结果若未通过准入，保留原始结果，向模型提供固定的 `result_too_large` 错误和真实短字段，
见[大工具结果的拒绝呈现](MODEL_IO_cn.md#61-大工具结果的拒绝呈现)。不为它另调压缩模型，也不重跑工具。
工具调用及其持久记录、请求、结果的编码上界仍在执行前检查；如果连准备记录或固定 Chat 回复都无法发布，报告错误并退出。

Agent 基础设施 RPC 重试耗尽时退出整个进程；工具业务失败不因此退出。
普通模型、压缩模型和工具等待截止时间均从原请求的 OpenEvent 顶层 `ts_ms` 加当前对应 timeout 计算，
分页读取共用首请求期限，重启不从恢复时刻重新计时。到期先保存一次触发事件，再按其 seq 与结果、取消的源 seq 裁决；
已经落盘的更早结果不因处理、展示或保存较慢而变成超时。触发记录和来源字段见 [WAL 协议](AGENT_WAL_PROTOCOL_cn.md#3-data-字段)。
等待期限配置不冻结；已经确认的接受、超时或失败不会因配置变化撤销。

## 模型工具与附件

模型只获得三项工具：

| 工具 | 参数和用途 |
| --- | --- |
| `exec` | 必填 `command`；可选绝对 `workdir`、正整数 `timeout_ms` 和本次需要访问的附件 `object_ids`。未指定目录时使用当前会话目录；未指定附件时不携带附件凭据。 |
| `read_stdout` | 必填已有结果中的数字 `exec_id` 和正整数 `nbytes`；可选 `offset`，读取 stdout 的明确字节范围。 |
| `read_stderr` | 参数同上，读取 stderr。 |

范围读取默认 `offset=0`，不维护隐式游标；成功时精确返回 `nbytes` 与本次输出额度中较小的字节数。
有效读取范围必须存在，空文件或越过文件末尾返回工具错误。
下一段位置是返回的 `offset + bytes`；`eof` 表示当前观察到文件末尾，`truncated` 表示额度导致这段范围没有读完。
两者可以同时为 true。输出能完整解码为 UTF-8 时返回文本，否则返回 base64，原始字节不丢失。
输出额度按原始字节计量，不代替请求准入检查；即使未超过该额度，完整编码仍可能过大，此时按[结果拒绝规则](MODEL_IO_cn.md#61-大工具结果的拒绝呈现)提供短错误。
执行结果保留真实退出码，并提供 Cmd 生成 run result 时观察到的 `stdout_bytes`、`stderr_bytes` 总字节数，供模型选择读取范围；
长输出未内联时也提供这些计数。没有取得实际 run result 的等待超时不提供 `exec_id` 或这些计数。
执行结果通过记录中的工具标识对应原调用，并作为真实结果事件进入后续输入；不包装成补齐原生工具对话的占位回执。
命令保留在调用参数中，正常和错误结果均不携带 `command`。

附件只在引用该附件的用户消息或其回复引用中包含名称、媒体类型、字节数和 `object_id`，不包含 ObjectKey 凭据或预下载路径。
原消息仍在历史事件中时，这些信息随原消息提供；后来的无关消息不会附带它们。压缩时由模型决定在摘要正文中保留哪些附件信息、丢弃哪些，
程序不维护或补发一份全历史附件清单。
模型需要内容时，在 `exec.object_ids` 中列出所需附件 ID，例如：

```json
{"command":"openevent-read-object 12345","object_ids":[12345]}
```

`object_ids` 只能选择本次冻结输入中未压缩用户消息及其回复引用的原始附件，或该输入采用的摘要所覆盖原消息及其回复引用的原始附件；
按首次出现顺序去重后最多 1024 个。Agent 沿原始 ObjectKey 取得凭据，不从摘要文字生成凭据；后来到达或其他会话的附件不能混入。
摘要决定模型能看到哪些附件信息，不撤销原消息已有的附件引用，也不要求把全部历史附件重新列给模型。
省略或传空数组时不携带附件，普通命令也不会自动取得全部附件。非法选择按模型输出校验失败处理，
本次回答中的工具均不执行。需要工作副本时，可将命令改为 `openevent-read-object 12345 > attachment.txt`。

命令成功时向 stdout 写原始对象字节；失败时非零退出，stderr 区分无效 ID、环境或依赖缺失、引用未登记、
引用格式错误和对象服务读取失败等原因，不包含凭据或内部路径。对象完整读取成功后才写 stdout，
仍须以退出状态判断是否完整写出。重定向得到的是可修改副本，不改变原对象。
Agent 将消息中的 `object_id` 与读取凭据登记在内存里，随历史读取恢复与更新，不要求历史正文常驻，也不另写 JSON、KV 或数据库。
Agent 只将本次 `exec.object_ids` 选中的附件凭据附在 Cmd 执行请求的顶层 `object_keys`；Cmd 按其协议将凭据交给命令的
`OPENEVENT_OBJECT_KEYS` 环境变量。命令从环境取得凭据，直接读取对象服务，执行时不依赖 Agent 在线。
Runtime 在 Cmd worker 环境中设置对象服务地址 `OPENEVENT_OBJECT_TARGET`，
模型不需要填写这些环境变量或对象凭据。通用 shell 仍有正常文件访问能力，这不是文件系统隔离机制。

## 停止、重启和排错

Agent 正常停止时停止发起新工作，等待已开始的 RPC 和发布确认完成；
停机本身不主动发送业务取消，也不等待远端模型或命令执行结束。
整套服务的停止步骤、对运行任务的影响及重启前提统一见 [Runtime 的启动、更新与停止](RUNTIME_RECONCILER_cn.md#启动更新与停止)。

配置或依赖报错先修复环境；RPC 重试耗尽查看 Agent 和 OpenEvent 日志；模型调用失败通知出现后，
修复 Provider 问题后，通过新的完整用户消息继续提出请求。不要删除 WAL 或替换辅助 Channel 来绕过失败。
